API Automation Framework

Smart CI-ready API tests with fast execution, PR integration, and failure categorization for leadership visibility.

Advantages of This Framework

  • Single reusable template — Add new APIs (e.g. Billing Account Transfer) by copying one folder and changing endpoint + data; minimal duplication.
  • Bearer token auto-refresh — Expired auth is detected (401); token is regenerated and the request is retried so tests do not fail due to authorization alone.
  • Dynamic test selection — Run by group (-Dgroups=Billing) or by class (-DtestClass=...), enabling faster PR and smoke runs.
  • Allure reporting — Rich, offline-capable reports with request/response attachments and history for demos and audits.
  • Environment-based config — Switch dev/qa/stage via -Denv=qa; no code change for different environments.
  • TDD-style coverage — Positive and negative scenarios (validation, auth, missing/invalid data) built into templates like Billing Account Transfer.

Execution Speed vs Legacy MT Scripts

Existing manual/MT scripts often take significantly longer due to full flows and sequential execution. This framework is designed for speed and scalability.

Aspect Legacy MT Scripts This Framework
Execution Long-running; full end-to-end flows Faster API-only runs; optional parallel and group/class filters
Scope control Often all-or-nothing Smart selection: run only Billing, Sanity, or a single test class
Feedback loop Slower feedback Quick feedback for PRs and demos (e.g. -Dgroups=Billing)
Result: Same quality of coverage with much less time per run when using groups and class-based selection — ideal for VP and GM demos and daily CI.

CI/CD & PR Build Integration

Tests are integrated with GitHub Actions so that every PR gets automated test runs and reports, with optional rerun without manual intervention.

PR-triggered runs

  • On every pull request to main / develop, the workflow runs the test suite.
  • Allure report is generated and published (e.g. GitHub Pages + artifacts).
  • A comment is posted on the PR with links to the latest report and this run’s report.

Smart test selection (Gradle + workflow)

  • Gradle: -Dgroups=Sanity, -Dgroups=Billing, or -DtestClass=... to run a subset of tests.
  • Workflow can use test_group / test_class inputs to run only relevant tests on PR.
  • Future: detect changed files and run only affected test classes for even faster PR feedback.

Rerun on failure (no manual intervention)

  • Build is marked as failed if any test fails, but Allure report is always generated (continue-on-error then explicit fail step).
  • Teams can re-run the same workflow (e.g. “Re-run all jobs”) to get a fresh run — same branch, same code; no manual re-trigger needed beyond clicking re-run.
  • Future: automated rerun (e.g. retry once on failure) can be added in the workflow for flaky mitigation.

Failure Categorization

Failures can be classified so leadership and teams see whether issues are due to microservices, data, auth, or environment — not just “test failed.”

Microservice / API

  • 5xx responses, timeouts, connection errors.
  • Tests: e.g. non-existent resource (404), server error (500).
  • Report and failure reason point to backend/API health.

Data / validation

  • 4xx validation (400, 422), missing/invalid payload.
  • Tests: missing locationId, invalid UUID, invalid metadata.
  • Failure reason points to test data or contract.

Authorization

  • 401 Unauthorized — framework retries with refreshed token so transient auth expiry does not count as a “test failure.”
  • Billing Account Transfer (and other secured APIs) use bearer token; expiry is handled automatically.

Environment / config

  • Wrong base URL, missing env vars, missing tenant/organization ID.
  • Tests: e.g. “no ABCFS-ORGANIZATION-ID” expect 400/403.
  • Failure reason points to configuration or environment.

By tagging tests and mapping failure reasons (e.g. in Allure or analytics), we can show dashboards: “X% microservice, Y% data, Z% env” for VP and GM reviews.

Future Advancements

  • CI/CD gates — Block merge when critical tests fail or when failure rate exceeds a threshold; optional per-environment gates.
  • Failure buckets in reports — Automatically tag failures (microservice / data / auth / env) and expose in Allure or a custom dashboard.
  • Smart test selection on PR — Run only tests affected by changed code (e.g. changed Java files → corresponding test classes) to keep PR feedback fast.
  • Auto-rerun on failure — Workflow retries failed tests once (or N times) before marking the build failed, reducing noise from flaky runs.
  • Extend template to more APIs — Reuse the Billing Account Transfer template pattern for other domains (subscriptions, invoicing, etc.) with minimal effort.

Billing Account Transfer — Demo Template

This API uses Bearer token in the Authorization header. If the token expires, the framework detects 401, regenerates the token, and retries the request so the test does not fail solely due to authorization. This is already implemented in the shared ApiClient and in the Billing tests.
